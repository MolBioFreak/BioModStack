# De Novo Binder Design: product outcome

Status: final product scope for the binder workflow completion tranche. This is a specification, not a claim that the product has completed acceptance or permission to run science, rent workers or deploy.

The [harmonization specification](de-novo-binder-harmonization.md) is the current implementation authority and status ledger. The [acceptance specification](de-novo-binder-design-upgrade.md) retains the complete scientific/product denominator and A01–A14/C01–C14 identifiers. The [implementation packet](de-novo-binder-concurrent-implementation-plan.md) assigns remaining work and verification. These documents are a single packet, not alternative plans.

## Product direction

Deliver one modality-aware **De Novo Binder Design** experience, with the delivered BC2 workspace as the interaction reference. Its starting-generator lineup is RFantibody, BoltzGen, PPIFlow and first-class BC2. Existing BMS RFD3 generation is unconditional monomer design, not a target-conditioned binder generator; retain it in the separate De Novo Design product, not as a fifth binder option. A generator remains its own scientific engine; a consistent workspace must not make all generators submit antibody requests or adopt BC2's preview requirements.

The operator chooses an applicable format/objective and generator, acquires and inspects its sources, configures its native settings, runs generation and reviews native results. The operator can stop there or select exact candidates and structure states for compatible optional operations, inspect descendants, compare with parents and repeat on another selected subset. Every parent and earlier result remains intact.

“Generation 2” is conversational shorthand, not a public product name, new schema suffix or new job namespace.

## Target and template experience

Every starting generator receives the full applicable target/template experience, not a filename field beside an otherwise polished settings form. Reuse the existing PDB ID/RCSB discovery, upload, saved run/Design, structure/preset library and project-source mechanisms. Show the exact selected document in the full Mol* view with synchronized sequence, chains and residue selections. A structural template/scaffold/framework is not the same object as a saved workflow configuration.

Target and template/seed sources remain independently inspectable. Supported multi-target/state models retain all of those sources and their identities; a seeded model does not silently assemble separately chosen structures into a complex. Model-specific formats, chain roles, masks, numbering and conversions stay at their current scientific owners. A sequence-only native input uses a sequence view rather than fabricated coordinates. A mode with no structural template requirement does not acquire one.

Switching engine, mode or section must not drop populated sources, deliberate clears, selections or settings. Restore the destination's own saved draft first; adopt only compatible source information into untouched fields. Preserve this through actual emitted requests and saved/reopened templates, not just local React state.

## Existing project management, not another workflow engine

Make project and workflow-setup context usable from the same binder workspace, and binder work discoverable again from Project detail, Jobs and Results. Reuse existing Project, workflow setup, adapter, launch-context and resource-link infrastructure. Complete missing binder adapters and context propagation explicitly; project infrastructure being present is not proof that every binder route is already connected.

Keep destination project membership, project step ancestry, scientific parent/Design lineage, and source-library provenance distinct. Choosing a source from a different project does not silently move it or change the destination. Standalone work remains supported. Do not create another project database, binder round coordinator, compulsory project or model-specific scheduling service.

## Complete delivery scope

The three original concurrent phases remain:

1. Generalize and repair existing authoring, refinement, results, project integration and the remote bridge. Finish wider BoltzGen and agnostic native PPIFlow initial generation, then separately retain, upgrade and verify PPIFlow's narrower uses in our refinement loop. These require real model/request, Python/script and Nextflow changes, not relabeling the current seed/partial-flow wrapper. Finish source/draft handoffs, selected-round UI and the remaining correction ledger.
2. Preserve and finish full native BC2 integration: settings, modalities, source tools, actions, native accounting/results, lifecycle, local/remote execution and a real candidate handoff. Credit delivered implementation rather than starting it over.
3. Finish independently selectable experimental LigandMPNN interface-context and blind-pose diagnostic paths, retaining separate raw evidence and truthful input/conditioning limitations. These are not ordinary redesign and are not automatically proof of binding or pose recovery.

Optional to run does not mean optional to deliver. The loop includes independent repack, anchors, supported PPIFlow, sequence redesign, prediction, full existing FrustraMPNN, Caliby and the existing GROMACS handoff. Keep model-owned native controls and results, not reduced workflow-local substitutes. Preserve supported legacy/historical requests without silently substituting scientific methods.

FrustraMPNN remains binder-local exploratory evidence, not direct cross-chain energetics. Pairwise Frustratometer remains deferred. Cutoff-policy CRUD, saved classification/reclassification and automatic dual-pass/fail or rejection machinery were superseded and are not deliverables. Raw independent diagnostics remain in scope.

## Processing quality and performance

Holistically review the reachable Python, scripts, Nextflow graph, data processing, publication, UI/source loading and runtime/bridge behavior. Fix demonstrated defects, remove obsolete duplication and harden real boundaries without changing science or adding proof-based restrictions. Measure equivalent before/after work so efficiency and speed claims are real; separate orchestration, data processing, cold setup, warm launch and native compute. This is mandatory delivery work with assigned owners, not an optional audit after the UI is finished.

## What finished means

Every retained generator and applicable input family is connected to usable source/template authoring, correct typed requests, native results, project/standalone navigation and compatible selected continuation. Save/reopen/clone/retry, repeated rounds, exact state identity and optional-stage isolation work. Authorized native local and existing-bridge remote runs, result return, worker-offline reopening and measured cold/warm lifecycle behavior provide the execution evidence. A real BC2-produced structure-bearing candidate must traverse continuation; a zero-yield run cannot demonstrate that handoff.

No new scientific thresholds, default protocols, automatic optimization, duplicate configuration authority, generic DAG editor, logging dashboard or readiness database is requested. Existing ownership, integrity and native input checks remain. Missing proof limits engineering completion claims; it does not become a new launch, restart or continuation restriction. Christian must approve any exact new restriction or consequential scientific method change.
