# Transactional first-install configuration

The existing setup entrypoint now supports a **configuration-only** transaction:

```sh
./start_ui.sh configure --document /absolute/path/install.json --json
./start_ui.sh recover --operation-id UUID --json
./start_ui.sh resume --operation-id UUID --json
```

`recover` and `resume` are synonyms: finish the recorded operation, not a fresh
candidate. `--document` on recovery optionally verifies the same validated input.
`--expect-document-sha256 HEX` pins the exact bytes read by configure/recovery;
there is no executable preview/plan token. Preview remains read-only and cannot
silently authorize execution. `configure` rereads and validates the document.

## Supported scope and outcomes

- Linux with local POSIX filesystems supporting durable directory/file fsync and
  atomic symlink creation/rename. HOME and XDG paths must be absolute.
- Existing `bms.install.v1` validation, cross-lane mutable-state isolation, fixed
  port policy, profile normalization and export formatting remain authoritative.
- First installation only. Any existing profile/export, checkout-local legacy
  core env, nonempty selected mutable storage, or legacy HOME state is rejected.
  Nothing is merged, migrated, backed up over, or overwritten. Empty state
  directories and externally located shared immutable assets are allowed.
- Paths containing whitespace or shell/dotenv metacharacters are rejected for
  apply; the existing export formats do not safely represent them. No source
  file is changed by configure, and storage directories/weights are not created.
- The persisted normalized profile pins the effective local CPU/memory defaults.
  Runtime environment overrides still win in the existing readers; configuration
  rendering itself ignores those overrides, as preview does. Use a clean runtime
  environment when verifying installed configuration.
- Tailnet selection is recorded in the journal/receipt only: **no ingress, service,
  registration, browser, acquisition, or scientific-admission action occurs**.
- Exit 0: `configured`, `recovered`, or `already_configured`. Exit 3: structured
  blocker/interruption; CLI syntax errors remain argparse exit 2.
  `configured` denotes successful completion of this command; `configuration_active`
  separately reports whether a complete readable generation exists after an error
  (e.g. interruption after activation but before receipt completion). `ready` is
  always false. The lock and configuration metadata are the only writes.

## Durability and recovery protocol

The config directory contains a persistent `configuration.lock` inode (flock is
released by process death), and `configuration-v1/journal.json` records a UUID,
validated document, original byte hash, HOME/XDG/source context, generated bytes,
SHA256s, ingress intent, and prepared/committed state. Files are mode 0600; newly
created directories are 0700. A temporary sibling journal directory is durable
before being renamed into the transaction namespace; recovery also recognizes a
completed journal left in that sibling directory. Writes use unpredictable,
exclusive mode-0600 temporary files and no-overwrite publication for new files;
pre-existing temporary names and symlinks are never followed. Write directories
must be real, owned directories (canonical HOME/XDG aliases are resolved first).
The lock must be an owned, single-link regular file, opened without following links.
Unrecognized preparing-directory contents block rather than being adopted.

1. Under the exclusive nonblocking lock, refuse any prior installation/state.
2. Durably write the journal before publishing anything.
3. Stage and fsync the three immutable files in `configuration-v1/generation`.
   Revalidate profile, runtime exports, ports, hashes and effective storage paths.
4. Create each destination as a no-overwrite symlink to
   `configuration-v1/active/{profile,core_runtime_env,compat_env}` and fsync its
   parent. These destinations **may be on different filesystems**. This sequence
   is **not** a multi-file atomic replacement. Before activation all newly
   published destination links are dangling; managed readers fail closed.
5. Atomically create the single `active -> generation` pointer on the config
   filesystem, then fsync that directory. Only now do all three destination links
   resolve to the complete generation. Verify everything before marking committed.

Recovery reuses the same identity and bytes, stages missing files, recognizes
already-created links, refuses conflicting files, verifies exports against the
current runtime formatting authority, and completes activation/receipt writing.
Before activation it repeats selected-storage, legacy HOME-state, and checkout-local
env checks, including immediately before the activation pointer is created. Only
exact destination symlinks belonging to this recorded transaction are exempt;
an unrelated database appearing during interruption still requires migration.
Repeated recovery/configure is idempotent. Modified documents, operation IDs,
HOME/XDG/source contexts, corrupted stages and incompatible renderer changes
produce blockers, not silent regeneration. Restoring missing *uncommitted*
stages is supported; modifying a committed generation is not.

No automatic rollback/deletion command is provided: this bounded first-install
protocol has no prior configured generation to restore. Existing installation
migration must be separately designed. If an unrelated file appears at a
publication destination, it is preserved and recovery blocks for operator review.

## Reader/writer inventory and consistency boundary

- Python `load_install_profile` and `resolve_installed_core_runtime_paths` check
  generation consistency before/after their reads. Existing default/error fallbacks
  cannot swallow incomplete managed configuration. Bootstrap discovery also checks.
- API, frontend, workflow-adapter, core-runtime and mobile-publisher shell launchers
  use `configuration_read_guard.sh` before/after export reads. A transaction
  appearing during the read is rejected, not mixed with legacy/default values.
  `scripts/bms` and the capability launcher also use this boundary. The core
  controller checks before direct Compose command construction.
- Electron `shellPaths` checks activation and all export/profile hashes before
  resolving managed state; explicit BMS_DATA does not bypass incomplete detection.
  Every profile-read return (missing file, malformed JSON, invalid shape included)
  and data-root selection rechecks for an interleaved writer. HOME/XDG identities
  canonicalize existing aliases consistently with Python.
- Legacy profile save/export share the writer lock and reject managed-generation
  mutation. Release env writing and the cooler-control env helper likewise refuse
  managed changes. The root recovery-artifact installer refuses this new managed
  first-install format pending a qualified integration workflow.

The generation is immutable after activation. Arbitrary direct file edits,
external writers that ignore the lock, hand-run Compose, manually sourced raw env
files, filesystem loss, malicious same-user mutation, and old checkouts lacking
these guards are outside the supported reader/writer consistency boundary.
Do not move HOME/XDG/config destinations or edit the journal/generation manually.
**The managed first-install release receipt transition is implemented.**
Configure success alone is not a usable released installation. Use the supported
authorized release path; do not remove the managed-write guard or edit committed
exports. General migration and scientific qualification remain separate gates.
The reader/writer, receipt, recovery, and fault-test contract is in
[Managed Configuration Release Integration Contract](Managed_Configuration_Release_Integration_Contract.md).

## Verification

`platform/api/tests/test_transactional_configuration.py` exercises real CLI writes
and runtime/export resolution in disposable HOME/XDG fixtures, injected failures
at journal/staging/publication/activation/recovery boundaries, abrupt process death,
lock contention, changed inputs/IDs, preservation of conflicts, repeated resume,
unsafe paths, and actual split filesystems (`/tmp` versus `/dev/shm`). Desktop path
tests consume the real setup CLI generation and reject interrupted/corrupt state.
No model qualification or whole-installer readiness is established by these tests.
